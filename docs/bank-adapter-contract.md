# Bank gateway contract, version 1

The worker uses one configured origin. Request content cannot select a host, URL, certificate, credential, callback or executable tool. Integrated mode requires HTTPS and a client certificate. The client verifies the server certificate and refuses redirects. The credential is read from a private file or environment variable, separately from every agent token.

## Submit

`POST /payments`

Headers: `Authorization: Bearer <bank credential>`, `Idempotency-Key: <payment id>`, `Content-Type: application/json`.

```json
{
  "id": "pay_0123456789abcdef01234567",
  "tenant": "bank-one",
  "request_hash": "64_HEXADECIMAL_CHARACTERS",
  "debtor_account": "internal-account-alias",
  "creditor_account": "internal-recipient-alias",
  "amount_minor": 5000,
  "currency": "GBP",
  "reference": "Invoice 101"
}
```

The payment ID is generated by ScoutBankAI and remains stable through dispatch and reconciliation. It is distinct from the caller's business idempotency key. Amounts are integer minor units; the currently accepted currencies GBP, EUR and USD use two decimal places.

The adapter must enforce account ownership, funds, recipient checks, applicable screening and the provider's own customer authorisation before accepting the instruction. It must record the idempotency key atomically with the payment operation. Repeating an identical instruction must not create a second transfer. A changed request under the same key must be rejected.

## Response and lookup

`GET /payments/by-idempotency/{payment_id}`

Both submission and lookup return a response bound to the original request:

```json
{
  "idempotency_key": "pay_0123456789abcdef01234567",
  "request_hash": "64_HEXADECIMAL_CHARACTERS",
  "bank_id": "bank_transaction_123",
  "status": "accepted"
}
```

Allowed statuses:

| Status | Required meaning | ScoutBankAI action |
| --- | --- | --- |
| `accepted` | Bank accepted the instruction but final outcome is pending | Keep reservation; poll status |
| `settled` | Bank authoritatively reports successful completion | Keep the budget consumed; mark settled |
| `rejected` | Bank authoritatively reports a terminal failure with no debit now or later | Release the reservation once |
| `unknown` | No authoritative outcome is available | Keep reservation; require reconciliation |

Terminal and accepted responses require a bank ID consisting of letters, numbers, underscores or hyphens. Responses must echo the original request hash and idempotency key. Unknown values, mismatched bindings, oversized responses, timeouts, redirects and unsuccessful HTTP responses all become `unknown`.

**A 404 lookup is not proof that a delayed payment cannot arrive later.** The worker never converts absence into rejection and never blindly resubmits an unresolved instruction. The gateway needs its own authoritative journal. If the provider lacks reliable idempotency lookup, the adapter must retain the mapping and resolve uncertain operations through that provider's supported process.

The adapter must not report provisional cancellation as terminal rejection. It must not report request receipt as settlement. These are financial semantics that transport tests alone cannot establish.

## Operational requirements

Keep idempotency records at least as long as the bank can receive or reconcile a delayed instruction, including after backup restoration. Do not silently expire them while ScoutBankAI still has unresolved work. Protect gateway credentials and mappings independently of agent applications. Pin the configured bank origin and restrict network egress.

The included `mock-bank` implements this contract for development only. Its funds are simulated. Unit and HTTP integration tests verify the wire contract; a real institution must verify its own payment mapping and authoritative statuses before enabling live transfers.
